# MVP-055: Artifacts Storage System

**Status**: Design Complete  
**Priority**: P0  
**Category**: Core Infrastructure  
**Dependencies**: Database Infrastructure, Agency System  
**Replaces**: Old Git Collections (git_objects, git_refs, repositories, git_artifacts)

---

## Overview

The Artifacts Storage System provides a unified way to store, version, and manage all agency-related content including:
- Agency definitions (specifications, configurations)
- Workflow products (reports, analyses, generated code)
- Research outputs (requirements, documentation)
- Deliverables from agent work

This system consolidates and replaces the previous git-based collections with a simpler, more powerful model tailored to multi-agent workflows.

---

## Problem Statement

Currently, the platform lacks a unified system for storing and versioning the artifacts produced by agents and workflows. The existing git-based collections (git_objects, git_refs, repositories, git_artifacts) are:
- **Over-engineered** for agent workflows (full git implementation unnecessary)
- **Complex** to integrate with (requires git internals knowledge)
- **Disconnected** from agency lifecycle and permissions
- **Not optimized** for human-readable text formats (JSON, Markdown, HTML, YAML, code)

Agents need a simple, powerful way to:
1. Store their work products with proper versioning
2. Control visibility based on roles and lifecycle state
3. Organize content in intuitive folder structures
4. Track history without git complexity

---

## Solution Architecture

### Two-Table Design

#### 1. **artifacts_system** - Agency System Artifacts
Stores agency definitions, specifications, and configuration with human-controlled publishing.

**Lifecycle**: Draft → Publish → Archive

**Use Cases**:
- Agency specifications (introduction, goals, work items, roles)
- Workflow definitions
- Configuration files
- Templates
- Database schemas

**Publishing Model**:
- Drafts can be edited by creators and specific roles
- Human approval required to publish
- Published version becomes "active" and is used by the system
- Publishing new version keeps old published version in history
- Archive state for deprecated/superseded artifacts

#### 2. **artifacts_work** - Workflow Work Products
Stores outputs from agent workflows with git-like versioning.

**Versioning**: Commits, HEAD, Tags, Merge/Rebase, Diffs

**Use Cases**:
- Research transcripts and summaries
- Generated reports and analyses
- Work-in-progress deliverables
- Iteration history
- Collaborative documents

## Virtual Path System

Artifacts use a virtual filesystem-like path structure for organization:

### Path Rules
- Must start with `/`
- Agency-scoped: `/agency_{id}/...`
- Folder-like hierarchy: `/agency_genesis/specifications/v1/agency-spec.json`
- Case-sensitive
- Allowed characters: alphanumeric, `-`, `_`, `.`, `/`

### Standard Directory Structure

```
/agency_{id}/
├── specifications/          # System artifacts: agency specs, configs
│   ├── introduction.md
│   ├── goals.json
│   ├── work-items.json
│   ├── roles.json
│   └── workflows.json
├── research/               # Work artifacts: requirements, analysis
│   ├── requirements/
│   │   ├── transcript.md
│   │   ├── summary.md
│   │   └── gaps.md
│   └── analysis/
│       └── stakeholders.md
├── deliverables/           # Work artifacts: final outputs
│   ├── reports/
│   ├── generated-code/
│   └── documentation/
├── validation/             # Work artifacts: validation reports
│   └── validation-report.json
└── templates/              # System artifacts: reusable templates
    └── work-item-template.json
```

## Role-Based Access Control

### Access Model

**Single Source of Truth**: Role definitions in `roles.json` specify artifact access permissions via `artifact_access` field.

Artifacts DO NOT store permission data - they only track creation metadata for audit purposes.

### Permission Resolution Flow

1. **User/Agent makes request** to access artifact at path `/agency_X/specifications/goals.json`
2. **System identifies requester's role** from authentication context
3. **System queries agency's role definition** for that role code
4. **System checks role's `artifact_access` patterns**:
   - `can_read`: Does `/agency_*/specifications/*` match the requested path?
   - `can_write`: Does pattern allow modification?
   - `can_create`: Does pattern allow creation?
5. **Permission granted or denied** based on pattern match

### Permission Rules

1. **Pattern Matching**: Use glob patterns in role definitions (e.g., `/agency_*/specifications/*`)
2. **Role Hierarchy**: Admins can override with special `artifact_access.admin: true` flag
3. **Lifecycle Gates**:
   - **Draft**: Only roles with `can_write` permission to the path
   - **Published**: Only roles with `can_read` permission (broader access)
   - **Archived**: Only roles with `can_read` permission (read-only enforced by state)
4. **Audit Trail**: `created_by_role` field tracks which role created artifact (audit only, not for permission checks)

### Role Schema - artifact_access

**Example: Work Item Architect Role**

**Old (roles.json)** - Redundant deliverables list:
```json
"deliverables": [
  {
    "id": "deliv_003_001",
    "title": "Work Items Catalog",
    "content": "Comprehensive JSON work items catalog"
  }
]
```

**New (roles.json)** - Path-based permissions:
```json
"artifact_access": {
  "can_create": [
    "/agency_*/specifications/work-items.json",
    "/agency_*/deliverables/work-items/*"
  ],
  "can_read": [
    "/agency_*/specifications/*",
    "/agency_*/research/requirements/*",
    "/agency_*/deliverables/work-items/*",
    "/agency_*/validation/*"
  ],
  "can_write": [
    "/agency_*/specifications/work-items.json",
    "/agency_*/deliverables/work-items/*"
  ]
}
```

**Pattern Syntax**:
- `*` matches any characters within a path segment
- `**` matches any number of path segments (not implemented initially, use multiple patterns)
- `/agency_*` matches any agency ID
- Exact matches take precedence over wildcards

**Special Flags**:
```json
"artifact_access": {
  "admin": true,  // Bypass all restrictions (for human-admin role)
  "can_read": ["/**"],  // Read-only access to everything
  "can_create": [],
  "can_write": []
}
```

Deliverable definitions stay in work-items.json where they belong.

## Content Format Support

### Supported Formats

| Format | Extension | Validation | Use Cases |
|--------|-----------|------------|-----------|
| `json` | .json | JSON parse | Specifications, configs, structured data |
| `markdown` | .md | Markdown lint | Documentation, reports, research |
| `yaml` | .yaml, .yml | YAML parse | Configs, deployment manifests |
| `html` | .html | HTML parse | Reports, visualizations |
| `go` | .go | Go syntax | Generated code |
| `python` | .py | Python syntax | Scripts, agents |
| `javascript` | .js | JS syntax | Frontend code |
| `sql` | .sql | SQL syntax | Database schemas, migrations |
| `text` | .txt | None | Plain text |

### Format Detection

1. **Primary**: Agent declares format explicitly
2. **Fallback**: AI-based detection from content
3. **Extension hint**: Use file extension if available

### Validation

On artifact creation/update:
1. Validate content matches declared format
2. Set `validation_status`: valid, invalid, pending
3. Store `validation_errors` if invalid
4. For system artifacts in "published" state: **must be valid**

## Git-like Operations (artifacts_work)

### Commit

```go
func (s *ArtifactService) Commit(
    agencyID, path, content, message, author, branch string,
) (*ArtifactWork, error)
```

1. Compute SHA-256 hash of content + metadata
2. Find current HEAD for branch
3. Create new artifact with parent_sha = current HEAD's commit_sha
4. Set is_head = true
5. Update previous HEAD to is_head = false
6. Return new artifact

### Checkout (Get HEAD)

```go
func (s *ArtifactService) GetHEAD(agencyID, path, branch string) (*ArtifactWork, error)
```

Returns artifact where `is_head = true` for given path and branch.

### History

```go
func (s *ArtifactService) GetHistory(agencyID, path, branch string, limit int) ([]*ArtifactWork, error)
```

Walk from HEAD backwards following parent_sha links.

### Diff

```go
func (s *ArtifactService) Diff(sha1, sha2 string) (string, error)
```

Compare content between two commits, return diff.

### Tag

```go
func (s *ArtifactService) Tag(sha, tagName string) error
```

Add tag to artifact's tags array.

### Merge (Simplified)

```go
func (s *ArtifactService) Merge(agencyID, path, sourceBranch, targetBranch, author string) (*ArtifactWork, error)
```

1. Get HEAD of both branches
2. Create merge commit with merge_parents = [source_sha, target_sha]
3. Content = target HEAD content (simple fast-forward or manual merge)

## State Transitions (artifacts_system)

### Draft → Published

**Trigger**: Human approval (API endpoint or workflow action)

**Requirements**:
- `validation_status` must be "valid"
- Content must not be empty
- Format must be valid

**Actions**:
1. Set `state = "published"`
2. Set `published_at = now()`
3. Increment version number
4. Update `allowed_roles` to include all agency members (if desired)
5. Create audit log entry

**Previous Published Version**: Remains in database with old version number

### Published → Archived

**Trigger**: Manual archival or new version published

**Actions**:
1. Set `state = "archived"`
2. Set `archived_at = now()`
3. Make read-only

### Draft → Draft (Update)

**Trigger**: Agent or user edits

**Requirements**:
- User must be creator OR have role in `allowed_roles`
- Must be in draft state

**Actions**:
1. Update `content`, `format`, etc.
2. Re-validate
3. Set `updated_at = now()`
4. Increment patch version

## Success Criteria

1. **Simplicity**: Developers can create/read artifacts with single API call
2. **Versioning**: Full history preserved for work artifacts
3. **Access Control**: Roles properly restrict artifact visibility
4. **Performance**: Path lookups < 50ms, commit operations < 100ms
5. **Validation**: Invalid content rejected before storage
6. **Integration**: Genesis Agency successfully stores all specs as artifacts
7. **Migration**: Old git collections removed, no data loss
